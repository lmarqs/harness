# render

`harness render` turns the three repository files, plus any [presets](presets.md), into the files each agent and
tool reads: native permission and hook configuration, mise wrappers, the harness skill and its links, and the managed
blocks inside human-written files. `harness render --check` reports drift without writing, and
`harness render --refresh` moves unpinned presets to their newest upstream commit.

## When to use it

| Situation | Command |
| --- | --- |
| You edited `.agents/harness.yaml`, `.agents/policy.yaml` or `.agents/hooks.yaml` | `harness render` |
| You turned a module on or off | `harness render` |
| A preset named by `extends` changed upstream and you want the change | `harness render --refresh` |
| You want CI or a reviewer to confirm rendered files match their sources | `harness render --check` |
| You want to see what would change | `harness render --dry-run` |

## How it works

1. Read the repository files, resolve `extends` at the commit recorded in the manifest (or, with `--refresh`, at the
   current upstream commit), and validate everything against the schema.
2. Compute every output: owned files, owned keys inside native files, managed blocks, links.
3. Compare with the manifest and the working tree.
4. Write what changed, delete what is no longer produced (for example the files of a module you turned off), and
   rewrite the manifest.

Rendering is deterministic: the same inputs produce the same bytes on linux and macOS, and a second run changes
nothing. Output depends on the repository files, the presets at their recorded commits and the `schema`, not on the
binary's version. See [presets](presets.md#resolved-commits) for how a preset's commit is recorded and moved.

### What render writes

| Output | Kind | Produced when | Contents |
| --- | --- | --- | --- |
| `.claude/settings.json` `permissions.allow`, `.ask`, `.deny` | owned keys | `agents.claude` declared | the [policy](policy.md#how-entries-render) for Claude |
| `.claude/settings.json` `hooks` entries whose command is the harness hook command, and `raw` entries | owned entries | `agents.claude` and `modules.hooks` | `SessionStart` and `PostToolUse` entries, plus `raw` hooks from `hooks.yaml` rendered as native entries |
| `.codex/rules/harness.rules` | owned file | `agents.codex` declared | the policy for Codex |
| `.codex/hooks.json` harness entries | owned entries | `agents.codex` and `modules.hooks` | as for Claude |
| `.codex/config.toml` keys that enable project hooks | owned keys | `agents.codex` and `modules.hooks` | |
| `.agents/skills/harness/SKILL.md` | owned file | always | the [harness skill](skills.md#the-harness-skill) |
| `.claude/skills/harness`, `.codex/skills/harness` | owned links | always, unless the skills directory is already a whole-directory link to `.agents/skills` | `../../.agents/skills/harness` |
| `.mise/tasks/worktree/create`, `.mise/tasks/worktree/remove` | owned files | `front_door: mise` | one-line wrappers |
| `.mise/tasks/verify` | owned file | `front_door: mise` and `modules.verify` | wrapper |
| `.mise/tasks/task` | owned file | `front_door: mise` and `modules.tasks` | wrapper |
| `.mise/tasks/ralph/_default`, `.mise/tasks/ralph/clean` | owned files | `front_door: mise` and `modules.ralph` | wrappers for `mise run ralph` and `mise run ralph:clean` |
| Managed blocks | blocks | see [Managed blocks](#managed-blocks) | |
| `.agents/.harness/manifest.json` | owned file | always | the ownership record, including each preset's resolved commit |

Lifecycle actions are not rendered: `harness` reads them from `hooks.yaml` and runs them itself
([lifecycle](lifecycle.md)).

### Merge-rendering native files

Agents read their configuration from fixed paths that people also edit. `harness` therefore owns only specific keys
and entries inside those files, never the whole file:

| File | `harness` owns | Everything else |
| --- | --- | --- |
| `.claude/settings.json` | `permissions.allow`, `permissions.ask`, `permissions.deny`; hook entries whose command is the harness hook command; hook entries rendered from `hooks.yaml` `raw` | preserved byte for byte: `env`, `model`, `statusLine`, `enabledPlugins`, `$schema`, other hooks, unknown keys |
| `.codex/config.toml` | the keys that enable the project's hooks | preserved byte for byte |
| `.codex/hooks.json` | harness hook entries and `raw` entries | preserved |
| `.codex/rules/harness.rules` | the whole file | other files in `.codex/rules/` are untouched and keep applying |
| `.claude/settings.local.json`, `*.local.toml` | nothing | never written; read only by `harness scaffold --import local` |

`render --check` compares the merged result, so a hand edit to an owned key is drift, and an edit anywhere else is
not.

### mise wrappers

With `front_door: mise`, each wrapper is a small script that starts with the generated header and hands its
arguments to `harness`:

```sh
#!/bin/sh
# generated by harness (schema 1): edit .agents/harness.yaml and run harness render
exec harness verify "$@"
```

| Wrapper | Runs |
| --- | --- |
| `mise run verify …` | `harness verify …` |
| `mise run task …` | `harness task …` |
| `mise run worktree:create …` | `harness worktree create …` |
| `mise run worktree:remove …` | `harness worktree remove …` |
| `mise run ralph …` | `harness ralph …` |
| `mise run ralph:clean` | `harness ralph clean` |

When the repository already defines a task with one of these names, `harness` never overwrites it. It writes the
wrapper under `harness:<name>` instead (for example `mise run harness:verify`, from `.mise/tasks/harness/verify`)
and lists the collision in the [adoption to-do](scaffold.md#the-to-do). Once the repository's own task is gone, the
next render writes the plain name.

Without the binary, a wrapper prints one line saying `harness` is not installed and exits non-zero: a verification
or task command that silently succeeded would claim work that did not happen.

## Managed blocks

A managed block is text `harness` owns inside a file people own. Only the text between the markers is generated.

```markdown
Text people wrote stays exactly as it is.

<!-- harness:begin commands -->
...generated...
<!-- harness:end commands -->

More text people wrote.
```

In `.gitignore`, YAML and TOML files the markers are comments: `# harness:begin <id>` and `# harness:end <id>`.

| Block id | File | Contents | Produced when |
| --- | --- | --- | --- |
| `commands` | `AGENTS.md`, `README.md` | the repository's commands: lint, build, verify with its lanes, worktree, task, ralph, in the front-door form | always |
| `files` | `AGENTS.md`, `README.md` | the clone-local paths (`.work/`, `.beads/`, coordinator `.ralph-tui/`), their owner and when they appear | always |
| `memory-index` | `AGENTS.md` | the files under `.agents/memory/`, linked | `modules.memory` |
| `policy-summary` | `AGENTS.md` | the effective policy by decision, with the source of each entry (built-in base, preset, repository) | always |
| `import` | `CLAUDE.md` (root, or `.claude/CLAUDE.md` when only that exists) | one line: `@AGENTS.md` | always, unless the file already imports `@AGENTS.md` |
| `ignore` | `.gitignore` | `/.work/`, and `/.beads/` when the tasks module is on, omitting any path the repository tracks | always |

Rules for blocks:

- A new block is appended at the end of its file. After that, you may move the whole block, markers included,
  anywhere in the file; `harness` updates it where it is.
- Never edit between the markers. `render` overwrites the edit and `render --check` reports it.
- Text from other tools' sections (for example a section `bd init` added) is untouched; blocks are bound to their
  markers, not to headings.
- Deleting a block's markers by hand is drift: `render` puts the block back. Turn the module off, or run
  [`harness remove`](remove.md), to remove a block.

## Drift check

`harness render --check` computes every output and compares it with the repository, writing nothing.

- Exit 0: everything matches.
- Exit 2: something differs. Each differing file, block or key is listed with the command that fixes it.
- Presets are compared at their recorded commits, so a change upstream never fails the check by itself.
- A harness skill that differs only because the binary is newer is not drift: `harness doctor` reports it as a note,
  and `harness render` refreshes the skill. Upgrading the binary alone never fails the check.

Run it in CI as an optional step:

```yaml
# .github/workflows/harness.yml
name: harness
on: [pull_request]
jobs:
  render-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: jdx/mise-action@v2
      - run: mise use -g github:lmarqs/harness@<tag>
      - run: harness render --check
        env:
          HARNESS_NO_UPDATE_CHECK: "1"
```

If the repository uses an `extends` preset from a private source, the CI job needs read access to that source.

## Schema migration

When the repository files use an older `schema` than the binary's, `render` migrates them, shows the diff and asks
before writing (`--yes` skips the question). When they use a newer one, `render` refuses and asks you to update
`harness` (exit 3).

## Reference

```text
harness render [--check] [--refresh] [--dry-run]
```

| Flag | Default | Meaning |
| --- | --- | --- |
| `--check` | off | Compare only; exit 2 on drift |
| `--refresh` | off | Re-resolve every preset declared without `@<ref>` to its current upstream commit and record it |
| `--dry-run` | off | Print what would be written or deleted; write nothing |

| Exit code | Meaning |
| --- | --- |
| 0 | Rendered, or `--check` found no drift |
| 1 | Error: invalid repository file, a preset commit that can be neither found nor fetched |
| 2 | `--check` found drift |
| 3 | Repository schema is newer than the binary, or a migration needs confirmation without a terminal |

Files read: `.agents/harness.yaml`, `.agents/policy.yaml`, `.agents/hooks.yaml`, `.agents/.harness/manifest.json`,
presets at their recorded commits (from `~/.cache/harness/` or their source), the native files listed above,
`AGENTS.md`, `README.md`, `CLAUDE.md`, `.gitignore`, `.mise/tasks/`, `.agents/memory/`, the git index (tracked paths).
Files written: the outputs listed in [What render writes](#what-render-writes).

## Examples

Allow a new command for agents and render it:

```sh
$EDITOR .agents/policy.yaml        # add [npm, run, typecheck] to shared.allow
harness render
git diff .claude/settings.json .codex/rules/harness.rules AGENTS.md
```

Turn Ralph off in a Terraform repository:

```yaml
# .agents/harness.yaml
modules: { hooks: true, verify: true, tasks: true, ralph: false, memory: true, skills: true }
```

```sh
harness render      # deletes .mise/tasks/ralph/* and the Ralph allow entries
```

## Guidelines

- Do commit rendered files together with the source edit that produced them, so the diff explains itself.
- Do review rendered permission diffs in pull requests: they are the effective change.
- Don't edit owned keys, owned files or block contents by hand; edit the source and render.
- Don't add `.claude/settings.json` to `.gitignore`: teammates without the binary rely on the committed file.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `--check` fails in CI but passes locally | Uncommitted rendered files or manifest | Commit the rendered files and the manifest |
| A preset change upstream does not show up | `render` uses the recorded commit | `harness render --refresh`, or move the preset's `@<ref>` |
| `--check` lists `AGENTS.md` block `commands` | Someone edited inside the markers | Move the text outside the markers, run `harness render` |
| A key you added to `settings.json` disappeared | It was inside an owned key (`permissions.*`) | Put the rule in `policy.yaml` |
| The harness skill link is missing | `.claude/skills` is a whole-directory link to `.agents/skills`, so no per-entry link is needed | Nothing to fix |
| Wrapper says `harness` is not installed | The binary is not on PATH | [Install](installation.md) it |

## Coexistence

Merge-rendering exists so `harness` can share native files with people and other tools. See
[compatibility](compatibility.md) for settings files, skill-link shapes, other tools' `AGENTS.md` sections and
`.gitignore`.
