# Glossary

## Objective

**Problem.** The documentation uses many words in a precise sense of its own, such as owned, seeded, receipt, lane or
landed, and readers arrive at a page from a search or a link without having read the page that defines them. A developer
or a coding agent who reads such a word in its everyday sense draws the wrong conclusion, for example about what removal
deletes or when work counts as done.

**Goal.** A reader who meets an unfamiliar term on any page can learn its exact meaning, and where it is explained,
without reading the pages before it.

## Terms

| Term | Meaning |
| --- | --- |
| Action kind | What a declared action does: `run` (a shell command), `http` (an HTTP request `the-cook` makes itself, with the URL and header values read from environment variables) or `attempt` (an unattended run of a declared worker under the attempt contract). Notification hooks take `run` and `http` only. |
| Actor | The identity of the work in a managed workspace, `<user>:<workspace>:<random>`, recorded when the workspace is created and passed to every event fired there as `COOK_ACTOR`, so a tracker's actions can assign a task to it. |
| Adopt | `the-cook scaffold --adopt`: take over an existing hand-written setup of a repository's workers, import what can be expressed, list the rest as a to-do |
| Adopted repository | A repository set up for `the-cook`, by `the-cook scaffold` with or without `--adopt`: it holds `.cook/`, the committed wrapper `cook` and the files `the-cook` renders. See [scaffold](scaffold.md) |
| Adoption class | Greenfield, brownfield-simple or brownfield-complex: the state a repository starts from. See [concepts](concepts.md#adoption-classes) |
| Agent harness | The program that runs a coding agent and reads its permissions, hooks and instructions: one kind of worker program, which a worker ingredient describes |
| Agent-content directory | `.agents/`: skills, memory, worker commands and the review guide. A convention of the coding-agent ecosystem, shared with other tools such as a skills installer, that stays meaningful without `the-cook`. See [concepts](concepts.md#two-directories-two-owners) |
| Always-on context | The [standing context](context.md) every session of a role receives: `always` entries, `static` ones included. Capped by `context.budget` |
| Application change | A change that touches a file matching `verify.app_paths`; it requires lane selection and a build |
| Attempt | One unattended run of a worker on one task, under the attempt contract: `the-cook attempt <worker>`, an `attempt` action, or a recipe's `attempt` step. It exits 0 only for a verified attempt. |
| Attempt contract | The rules every attempt runs under: the worker's pinned unattended launch with `unattended.deny` applied, its floor bypass arguments refused, rules read from the base commit, the tamper check, and no pushes or lifecycle events of the worker's own. `the-cook attempt` also reports an attempt as verified only after a passing replay from the base, and releases a loop runner's completion signal only then. |
| Attended run | A recipe run someone drives, a person or a coordinating worker for one: every run started without `--unattended`, with a terminal or without. A handoff pauses it, fires nothing and exits 3, and `the-cook make --continue` resumes it. Compare unattended run. See [recipes](recipes.md#attended-and-unattended-runs) |
| Attention | The worker event for a worker waiting for a person: a permission prompt, a question, idle input. Its `run` and `http` actions are declared under `attention` in `hooks.yaml`; rendered from the native event the worker's ingredient maps to it |
| Bare string | A policy string that matches none of the native rule patterns of any declared worker's ingredient (`native_rules.patterns`): shorthand for a shell command rule, rendered only for workers whose ingredient can express it. See [policy](policy.md#entry-forms) |
| Base | The commit a change is measured against: a managed workspace's starting commit, or the merge-base with the default revision |
| Block | See Managed block |
| Blocked | The out-of-band lifecycle event for work that stops unfinished or needs a person. `the-cook` fires it when a command without a terminal exits 3, and when a recipe run stops; `the-cook make` goes by `--unattended` instead of the terminal. A person, a coordinating worker or a script around a loop runner fires it with `the-cook lifecycle run blocked`, for example when an unattended run stops unfinished. Its actions receive the reason in `COOK_REASON`. |
| Bootstrap | The profile's list of commands that prepares a checkout: run in a new managed workspace, and once per checkout an attempt runs in |
| Budget | A limit on the lines `the-cook` adds to what workers read every session: `blocks.agents_md_budget` for the blocks in `AGENTS.md` (default 40, 8 per block), `context.budget` for always-on context (default 120 per role). `doctor` notes an overrun. |
| Cache | `$COOK_HOME`, default `$XDG_CACHE_HOME/the-cook`, or `~/.cache/the-cook` when `XDG_CACHE_HOME` is unset: the per-user directory holding downloaded releases at `versions/<version>/the-cook`, ingredient, station and recipe archives at `cookbook/<sha256>.tar.gz`, the update-check result and the result of `doctor`'s signed-checksum check, and nothing else |
| Checks | The part of an ingredient that `doctor` and `ingredient list --cookbook` use: a version command with the supported range, and a detect rule. See [ingredients](ingredients.md#checks) |
| Configuration directory | `.cook/`: the profile, policy, hooks file, `wrapper.yaml` and manifest, and the repository's recipes in `.cook/recipes/`. It is versioned, holds no state and is never ignored. Both removal modes delete every file `the-cook` recorded there and `.cook/recipes/`, listing each recipe in the plan first, and the directory once nothing else is in it |
| Context trigger | What makes a `when` entry of [standing context](context.md) fire: `paths` (the worker first reads or edits a matching file) or `prompt` (the person's message contains a listed word or phrase) |
| Contract | One of the three interfaces the binary declares and an ingredient's operations fill: the version-control contract, filled by the ingredient `vcs:` names; the worker contract, filled by one ingredient per declared worker; and the optional jail contract, filled by the ingredient a worker's `jail` names. An ingredient fills at most one, and declares the contract's version it is written for. A command that needs the version-control or a worker contract that no pinned ingredient fills exits 3, naming `station apply` and `ingredient pin`. See [ingredients](ingredients.md#contracts) |
| Convention block | A managed block that states, as plain fact, a convention that stays true without `the-cook`, and never names a `the-cook` command: `workspaces`, `policy`, `memory` and `context` in `AGENTS.md`, the `import` block a worker ingredient renders into its worker's instruction file, every `.gitignore` block. An eject keeps its text. See [concepts](concepts.md#convention-blocks-and-tool-blocks) |
| Cookbook | A source that publishes ingredients, stations and recipes by version: an HTTPS base URL or `github:<owner>/<repo>`, where each tag holds one archive per unit, named by its kind, `ingredient-<name>.tar.gz`, `station-<name>.tar.gz` or `recipe-<name>.tar.gz`, and one checksum file, `checksums.txt`, with the sha256 of every archive of the tag. Every ingredient and station a repository uses, and every recipe it copies, comes from a cookbook; `the-cook` holds no default cookbook. See [stations](stations.md#cookbooks) |
| Coordinating worker | A worker session, attended or left alone, that drives work through `the-cook` commands for a person, for example starting a loop runner in a managed workspace, arranging the run's commits and firing `completed` or `blocked` with scope `run`, then `deliver`. Work that needs an MCP tool is its job, since `the-cook` never connects to an MCP server. See [safety](safety.md#unattended-runs) |
| Default branch | The name of the shared default line of work, as the version-control ingredient's `default_branch` reports it. Used as a name: by floor rules through `{default_branch}`, in `COOK_DEFAULT_BRANCH`, and by the delivery guard against the default branch. Compare default revision |
| Default revision | The revision the shared default line of work is at, as the checkout last learned it, which the version-control ingredient's optional `default_revision` reports, such as `origin/<branch>` for a git ingredient; without it, the default branch. Used as a commit: the base of the workspace a recipe run creates, the target of landed detection and the start of a fleet delivery branch. See [ingredients](ingredients.md#the-version-control-contract) |
| Deliver | The lifecycle event that sends concluded work out of the clone through declared actions (push, pull request, CI trigger). Guarded: never on the default branch or with uncommitted changes and, when the verify module is enabled, never without a valid receipt. |
| Detect rule | File globs whose match shows that a station fits a repository, which `scaffold --cookbook` uses to choose stations, or that an ingredient's program is in use, which `ingredient list --cookbook` shows. See [stations](stations.md#detect-rule) |
| Drift | A difference between an owned file, key or block and what the sources produce with the pinned release; reported by `render --check`. No owned artefact is exempt |
| Eject | `the-cook remove --eject`: stop managing a repository and keep the result. Convention blocks lose their markers and keep their text. Tool blocks, the shipped skill, hooks that run `cook` and permission entries that name a `the-cook` command are removed. `.gitignore` entries, the other permissions and `raw` hooks stay as hand-owned content. `cook` and the owned and seeded files of `.cook/` are deleted, and `.cook/` once nothing else is in it. |
| Entries | The part of a station that adds to the profile, the policy and the hooks file: applied once by `station apply` or `scaffold --cookbook`, only where missing, and the repository's own afterwards. See [stations](stations.md#entries) |
| Equivalence check | The adoption step that compares, per worker, the effective rule set after import with the one before it; a lost project rule makes adoption exit 2. See [scaffold](scaffold.md#the-equivalence-check) |
| Fingerprint | A hash over the base and the path, mode and content of every changed file; binds a receipt to content |
| Fleet | An explicit list of repositories that `the-cook fleet` runs a command across |
| Floor | Deny rules and bypass arguments an ingredient marks as facts no repository may lose: rendered into every worker's output on every render, refused at every unattended launch, never written into the policy and out of its reach. Examples: a version-control ingredient's deny of a force push to the default branch, a worker ingredient's bypass arguments. See [ingredients](ingredients.md#the-floor) |
| Greenfield | A repository with no worker permissions, hooks or workflow engine of its own |
| Handoff | A recipe [step](recipes.md#handoff) that prints its text for whoever drives the run, a person or the interactive worker in their session, and exits 3. In an attended run it pauses the run and fires nothing; in an unattended run it stops the run as blocked, firing `blocked`. `the-cook make --continue` resumes either with the next step |
| Hooks file | `.cook/hooks.yaml`: worker-neutral hook declarations, notification hooks and lifecycle actions. See [hooks](hooks.md) |
| Import scope | Where `scaffold --import` reads existing configuration: a comma-separated set from `project`, `local`, `user`, `none`; `project` by default with `--adopt`, `none` without it |
| Ingredient | A named, versioned description of one program, in data the binary interprets: operations that fill one contract or none, renders, floor and checks, and no entries or templates. Published in a cookbook and pinned in the profile under `ingredients:`; cached under its hash and checked on every load. See [ingredients](ingredients.md) |
| Inject | How a standing-context entry reaches a session: `content` (the text itself) or `pointer` (one line naming the skill or file to read now) |
| Input | A value a recipe run takes, declared in the recipe with a type, `string`, `slug`, `enum` or `bool`, and a name of lowercase letters, digits and `-`, starting with a letter, that is not a flag `the-cook make` accepts. Given as `--<name> <value>`, a `bool` as `--<name>` alone; substituted into placeholders, and passed to `run` steps as `COOK_INPUT_<NAME>`, upper case with each `-` as `_`. See [recipes](recipes.md#inputs) |
| Interactive | A worker role: people use the worker in this repository |
| Invariant | A rule of the process built into the binary that no repository file or flag can turn off. The facts about a program it applies, such as a worker's bypass arguments, come from that program's ingredient as floor. See [concepts](concepts.md#built-in-invariants) |
| Issue | A GitHub issue: part of the team's record of work. `the-cook` never writes issues |
| Jail | A program that runs another program confined to the directories it shares read-only or read-write, the variables it passes and the network it opens, using the host's own programs at their own paths. A worker declared with `jail` runs its attempts, and the replay of their work, inside one; interactive sessions never do. A container image or another machine is not a jail: the whole recipe run or loop run runs there instead. See [workers](workers.md#jails) |
| Jail contract | The contract a jail ingredient fills: its launch, separator and working-directory share, the arguments for write shares, read shares, passed variables or an inherited environment, and the network, and the floor bypass arguments that would turn its confinement off. See [ingredients](ingredients.md#the-jail-contract) |
| Knowledge | Prose, memory and skills written by people and workers; never generated by `the-cook` |
| Landed | The lifecycle stage and event for a recorded branch whose patches are all in the default revision, as the version-control ingredient's `landed` operation reports. `workspace remove` fires it before removing the workspace, first learning what is shared when `workspaces.update_before_landed` is set; `the-cook lifecycle run landed` fires it manually; `doctor` only reports landed branches, against what the checkout knows |
| Lane | A named family of test commands in the profile, with a `select` command, an optional `full` command and `required_when` globs |
| Lifecycle | The software development lifecycle `the-cook` declares and runs, its core abstraction: the stages a change goes through (Plan, Start, Implement, Verify, Complete, Deliver, Review and merge, Landed, and `blocked` out of band), the events fired between them, the guards that hold between stages and the proof a change carries. A stage that needs a program reaches it through a contract or a declared action. A recipe run is one pass of one change through the stages. |
| Lifecycle action | A named action a repository declares under an event in `hooks.yaml` `lifecycle`, of one action kind; it runs in the work's checkout and receives values only through `COOK_*` environment variables |
| Lifecycle event | One of `start`, `verified`, `completed`, `deliver`, `landed`, and the out-of-band `blocked`: a point between stages of the lifecycle at which declared actions run. |
| Loop run | An unattended run of a loop runner whose command for each task is `the-cook attempt <worker>` or `the-cook make <recipe> --unattended`: the loop runner picks each task, and the attempt, or the recipe run, runs the worker on it under the attempt contract. Also called a Ralph loop in agentic coding. |
| Loop runner | A third-party program that works through a list of tasks and starts a worker for each. The binary contains no code for any; a loop runner connects by naming `the-cook make <recipe> --task <id> --unattended` or `the-cook attempt <worker>` as the command it runs for each task, typically through a template a station writes. See [recipes](recipes.md#a-loop-runner-runs-implement-task-for-each-task) |
| Managed block | Text inside a file people own, between `<!-- cook:<id> -->` and `<!-- /cook:<id> -->` in Markdown, or `# cook:<id>` and `# /cook:<id>` in `.gitignore`, YAML, TOML and shell files; written only by `the-cook`. Each module owns its block ids. See [render](render.md#managed-blocks) |
| Managed workspace | A workspace created by `the-cook workspace create` under `workspaces.dir` (default `.work/workspaces/`), with a recorded session |
| Manifest | `.cook/manifest.json`: the record of every owned file, key, entry and block and every seeded file, with hashes and the schema |
| Memory | Durable, reviewed repository knowledge for workers under `.agents/memory/`, indexed in `AGENTS.md`. See [memory](memory.md) |
| Merge-render | Writing only owned keys and entries into a native file and preserving everything else byte for byte |
| Module | An opt-in feature set in the profile: `hooks`, `verify`, `memory` |
| Native file | A file a worker reads from a fixed path, which its ingredient names and renders |
| Native rule string | A policy string that matches a native rule pattern of a declared worker's ingredient (`native_rules.patterns`), in that worker's own rule syntax; rendered verbatim for the workers whose patterns it matches |
| Notification hook | An action declared under `attention` or `turn_end` in `hooks.yaml`: `run` or `http`, fired by the worker's own notification events, never in an attempt. See [hooks](hooks.md) |
| Operations | The part of an ingredient that fills a contract: commands with placeholders and a declared output kind (string, lines, bytes or status), and mappings the binary reads as data. See [ingredients](ingredients.md#operations) |
| Origin | The `origin` key of a recipe copied from a cookbook: the cookbook, the tag and the sha256 of the archive it came from. Written by `recipe add` and `station apply`, and moved to the newer version by `recipe update` when it merges that version into the copy, from the version `origin` names, whether or not the merge leaves conflicts to resolve. Absent from a repository's own recipes. Unlike a pin, it is not read when the recipe runs. See [recipes](recipes.md#updating-an-added-recipe) |
| Owned | Written, rewritten and tracked by `the-cook` through the manifest; never edited by hand. Compare seeded |
| Pending pin | A pin without checksums, `checksums: pending`, written by `the-cook scaffold --offline` because a binary cannot contain its own checksums and offline cannot fetch them. Nothing downloads against it; a cached release still runs. `the-cook wrapper --version <the pinned tag>` completes it, and `doctor` reports it until then. |
| Ingredient pin | An `ingredients:` entry with `name`, `source` (the cookbook), `version` (the tag) and `sha256`, written by `the-cook ingredient pin`, `station apply` or `scaffold --cookbook`; the binary checks every archive against it on download and on every load. See [ingredients](ingredients.md#pinning) |
| Release pin | The release recorded with the sha256 of each platform's binary in `.cook/wrapper.yaml`, owned content, written by `scaffold` and moved only by `the-cook wrapper` after verifying the release's signed checksum file; a global install defers to it. See [wrapper](wrapper.md), Pending pin |
| Station pin | A `stations:` entry recording which station was applied at which version, with no effect on what renders. See [stations](stations.md#after-applying) |
| Policy | `.cook/policy.yaml`: which commands workers may run without asking, only after asking, or never. See [policy](policy.md) |
| Profile | `.cook/config.yaml`: the repository's facts for `the-cook`. See [profile](profile.md) |
| Raw entry | A hook in `hooks.yaml` `raw`, rendered as a native hook entry that runs without the binary |
| Receipt | `verified.json` in a checkout's state directory (default `.work/`): the record of a passing `the-cook verify`, bound to the base and the fingerprint, with the patterns each lane ran or that it ran in full. A recipe run's Verify writes its own, which also records the recipe, its digest and the inputs |
| Recipe | One kind of change a repository makes many times: the inputs it takes, what it requires of the repository, the steps that make the change, mapped onto the stages, and the lanes that must prove it. Copied into `.cook/recipes/<name>/` from a cookbook, with its origin, or written there by the repository, and the repository's own to edit; it acts only when someone runs it with `the-cook make`. See [recipes](recipes.md) |
| Render | Produce native files, `cook`, the skill, links and blocks from the repository files, the pinned release and the pinned ingredients. Also one of the parts of an ingredient: content the binary owns and writes on every render, recorded in the manifest under the ingredient's name. See [render](render.md), [ingredients](ingredients.md#renders) |
| Replay | `the-cook attempt` rerunning the lanes a worker's receipt selected, with the profile read from the base commit, before it reports the attempt as verified; a recipe run replays its own receipt the same way at Complete |
| Role | How a worker is used in a repository: `interactive` or `unattended` |
| Run | One pass of one change through the lifecycle stages by a recipe, started by `the-cook make <recipe>`. Reads its recipe once at Start, runs the steps at Implement, verifies at Verify, and replays from the base at Complete. See [recipes](recipes.md#the-run) for run mechanics |
| Schema | The format version carried by every repository file, ingredient, station, recipe and rendered artefact |
| Scope | What a lifecycle event concerns: `task` (one tracked task), `run` (a whole unattended run of a loop runner, fired only by whoever drives it; not a recipe run) or `change` (work without a task, such as a fleet change) |
| Seeded | Written once and owned by the repository from then on: `.cook/config.yaml`, `.cook/policy.yaml` and `.cook/hooks.yaml`, by `scaffold`; the `.agents/memory/` skeleton, when the memory module is enabled, by `scaffold` or the first `render` after it. Recorded in the manifest with the hash it was created with, never re-rendered. |
| Session | A managed workspace's record in `session.json` in its state directory: the base, the task id given with `--task`, the actor |
| Shared default line of work | The line of work every clone of the repository shares as its default: for git, the default branch as the shared repository holds it. Its name is the default branch, and where this checkout last learned it to be is the default revision. A checkout learns what is shared only through the version-control contract's optional `update`, which `fleet --deliver` runs, and `workspace remove` runs when `workspaces.update_before_landed` is set. See [ingredients](ingredients.md#the-version-control-contract) |
| Shipped skill | `.agents/skills/the-cook/SKILL.md`: the tool-owned skill teaching workers the standards and their reasoning |
| Skip reason | Free text recorded in the receipt for a lane not run |
| Stage | One of the parts of the lifecycle a change goes through, in order: Plan, Start, Implement, Verify, Complete, Deliver, Review and merge, Landed. A station's stages say which ingredient serves the stages that need a program: version control, and the workers that act at Implement. A recipe maps its keys onto the stages. See [stations](stations.md#stages), [recipes](recipes.md#overview) |
| Standing context | Directives and skills `the-cook` puts into worker sessions when a declared trigger fires (`always`, `paths`, `prompt`), so nobody invokes them by name; declared in the profile's `context` section. Hooks deliver them, except the `always` entries of an attempt whose prompt arrives on stdin, which travel in the prompt. See [context](context.md) |
| State | Clone-local, gitignored, disposable data `the-cook` writes at the paths the profile sets (`state.dir` and `workspaces.dir`, both under `.work/` by default). See [profile](profile.md#state-paths) |
| Station | A named, versioned description of what one way of working needs in place, built from ingredients: the ingredients it pins, its stages, which declare the workers and their roles, entries for the profile, the policy and the hooks file, templates, the recipes it adds, each pinned by sha256, and a detect rule, and no renders or floor. Published in a cookbook and applied once, after which its entries, templates and recipes are the repository's own; recorded in the profile under `stations:`. See [stations](stations.md) |
| Step | One action of a recipe at the Implement stage, of a kind from a closed set the binary defines: `run`, a command as an argument list; `template`, a file written from the inputs; `attempt`, a declared unattended worker on a prompt, under the attempt contract; `handoff`, text for whoever drives the run, which pauses an attended run and stops an unattended one. A failed step stops the run. See [recipes](recipes.md#step-kinds) |
| Tamper check | Before an attempt's worker starts, the restore of the tool-owned files to their state when the attempt began; after it exits, the comparison of those files, the files under `.cook/` and the files standing context names with that state. Any difference fails the attempt. For `the-cook attempt` run on its own that state is the base commit's; for a recipe's `attempt` step it is the workspace as the step found it, uncommitted edits included. `attempt` actions run it too |
| Task | A unit of work in the tracker a team uses, named by a free-form id. `the-cook workspace create --task <id>` binds a workspace to it, and every event fired there carries it as `COOK_TASK`. |
| Template | A whole file in a station or in `scaffold`, rendered once with values from the profile and written only when the file is absent. From then on it is the repository's own file: `the-cook` never re-renders or removes it, and `station apply` reports `kept <path>: exists` and leaves it. Example: a loop runner's configuration file a station writes. One of the parts of a station. A recipe's [`template` step](recipes.md#template) writes one in each run, from a file of the recipe rendered with the run's inputs, and refuses a path that exists. See [stations](stations.md#templates) |
| To-do | The list of adoption items `the-cook` cannot resolve deterministically, printed by `scaffold --adopt` and reported by `doctor` |
| Tool block | A managed block that says how to use `the-cook` in this repository and may name `./cook` commands: `commands`, `layout`, `verify` and `lifecycle` in `AGENTS.md`, `commands` in `README.md`. An eject removes it. See [concepts](concepts.md#convention-blocks-and-tool-blocks) |
| Tracker | The tool a team keeps its tasks in, such as an issue tracker or a tracker that keeps its database in the clone; the binary contains no code for any. Lifecycle actions on `start`, `completed` and `blocked` that read `COOK_TASK` and `COOK_ACTOR` wire it, as a station may write them. |
| Trigger point | The place in a `the-cook` command where an event fires automatically, running the actions declared with `auto: true` |
| Trust chain | How a release becomes trusted: each release publishes a checksum file and its signature, every binary embeds the release keys it trusts, and a pin changes only after an already trusted binary verifies the new release's signed checksum file. The first binary a person installs is the root. See [wrapper](wrapper.md#security) |
| Turn end | The worker event for a worker finishing a turn. Its `run` and `http` actions are declared under `turn_end` in `hooks.yaml`; rendered from the native event or setting the worker's ingredient maps to it |
| Unattended | A worker role: the worker runs here only in attempts, under `the-cook attempt`, an `attempt` action or a recipe's `attempt` step, and its native files also carry `unattended.deny` |
| Unattended run | A recipe run started with `the-cook make --unattended`, which its caller passes when nobody drives the run, as a loop runner does: a handoff stops it as blocked and fires `blocked`, and `--here` is refused. Compare attended run. See [recipes](recipes.md#attended-and-unattended-runs) |
| Undo | `the-cook remove` without `--eject`: delete the owned content, every block and its text included, the seeded files in `.cook/`, and the memory skeleton files that still match the hash they were seeded with; write back the settings adoption imported from the project's native files; list and leave any file the manifest does not record. |
| Validator | A repository check: a command run when a changed or edited file matches its `when` globs. Those under `verify.validators` in the profile run in `the-cook verify`; those under `validators` in `hooks.yaml`, which may reuse the profile's, run after a worker edits a file. See [profile](profile.md#verify), [hooks](hooks.md) |
| Version-control ingredient | The ingredient `vcs:` names: it answers every question about the repository's history, such as the base commit, the default branch and what changed. See [ingredients](ingredients.md#the-version-control-contract) |
| Worker | A program that changes the repository for someone, such as a coding agent, a bot or a codemod. Declared in the profile under `workers.<name>`, with the ingredient that fills its worker contract, its role, whether its attempts may use the network and the jail they run in, if any. See [workers](workers.md) |
| Worker contract | The contract a worker ingredient fills: its launch, its unattended arguments, its network arguments, its floor bypass arguments, its hook payload mapping, its instructions file, its skill location, its native rule import and its renders; every item is optional except the launch. See [ingredients](ingredients.md#the-worker-contract) |
| Worker events | The events a worker program fires in a session: session start, post edit, prompt submit, attention and turn end. Hooks in `hooks.yaml` act on them, rendered into the native events the worker's ingredient maps them to. See [hooks](hooks.md) |
| Worker ingredient | An ingredient that fills the worker contract for one program: its native files, its launch, its bypass arguments, its hook payload mapping. Named by `workers.<name>.ingredient`, by default the worker's name. See [ingredients](ingredients.md#the-worker-contract) |
| Workspace | A separate working copy of the clone for one task, with its own branch, made and removed by the [version-control ingredient](ingredients.md#the-version-control-contract). The core never uses a version control system's own name for it |
| Wrapper | `cook`: the committed POSIX `sh` script at the repository root that runs the pinned release, downloading it and verifying its checksum the first time a machine needs it. The default entry point for people, workers, hooks and the loop runners that call `./cook attempt`. See [wrapper](wrapper.md) |
