# Skills

## Objective

**Problem.** An agent knows about a repository only what it reads there. Asked to change the repository's agent setup,
it does not know the rules for doing so and edits the wrong files or weakens a permission. A skill a team maintains for
many repositories, copied into each by hand, goes stale in some of them, and a skill that should guide every relevant
session guides only those where the agent happens to judge it relevant.

**Goal.** Every agent in the repository can read how to work with its agent setup, the shared skills the repository
carries are present and identical in every clone, and a skill the repository wants applied without anyone asking
reaches every session it covers and no other.

## Overview

Skills are folders of instructions agents load on demand. They live in `.agents/skills/`, the repository's
agent-content directory, one folder per skill. `harness` does two things with them. It installs and refreshes its own
skill, the **harness skill**, in every adopted repository. It injects skills into agent sessions when the repository
names them as [standing context](context.md). It never writes a domain skill, and it contains no code for any skills
installer: shared skills are installed by the team with the tool of its choice and committed like any other file
([ADR 0022](../adrs/0022-tool-integration.md)). The `skills` [plugin](plugins.md#skills) describes one such tool, the
`skills` CLI.

Commands are named `harness <command>` on this page. The examples run them through the repository's wrapper,
`./harnessw <command>`, from the root of a checkout; with a global install, `harness <command>` is equivalent
([wrapper](wrapper.md)).

## The harness skill

`.agents/skills/harness/SKILL.md` is a tool-owned file, written by `scaffold` and refreshed by every `render`. Like
every owned file, it is drift-checked by the pinned release: it must match the text that release embeds, and an upgrade
refreshes it in the same change that moves the pin ([wrapper](wrapper.md#upgrading),
[ADR 0007](../adrs/0007-ownership.md)). Its header, the `# generated by harness` line that marks every owned file
([concepts](concepts.md#marking)), is a YAML comment on the line after the opening `---` of its front matter, so agents
and skills installers still read the front matter. It carries the same text as [`harness explain`](explain.md): the
standards `harness` applies and the reasoning behind each, written for an agent.

It teaches an agent to:

- run every `harness` command through the repository's wrapper, `./harnessw <command>`, from the root of the checkout
  it works in;
- edit `.harness/config.yaml`, `.harness/policy.yaml` and `.harness/hooks.yaml` correctly, then run
  `./harnessw render`;
- place a policy entry in `allow`, `ask`, `deny` or `worker.deny`, and explain why;
- finish an adoption from the `harness doctor --json` to-do ([doctor](doctor.md));
- choose lanes and write skip reasons for [`harness verify`](verify.md);
- run unattended work through [`harness worker`](ralph.md), and report blocked work;
- fire lifecycle events with `harness lifecycle run <event>`, including `completed` or `blocked` when a loop runner's
  run ends, and delivering the run's commits after arranging them for review;
- declare lifecycle and notification actions of the right kind (`run`, `http` or `agent`), with secrets read from
  environment variables;
- declare standing context: which skill or directive applies always, on which paths, or on which words, and preview
  it with `./harnessw context show`.

Agents find it where they look for skills. Each agent's [harness plugin](plugins.md#the-harness-contract) names that
location, and `render` writes a link there:

| Harness plugin | Path | Shape |
| --- | --- | --- |
| claude (Claude Code) | `.claude/skills/harness` | a link to `../../.agents/skills/harness` |
| codex (Codex) | `.codex/skills/harness` | a link to `../../.agents/skills/harness` |

When `.claude/skills` (or `.codex/skills`) is already a link to the whole `.agents/skills` directory, the skill is
reached through it and no extra link is written. When it is a real directory, the link is added inside it and nothing
else there changes.

`harness` lists the skill in no installer's lock file, such as `skills-lock.json` of the
[`skills` CLI](https://github.com/vercel-labs/skills), so no installer manages it. `harness remove` and
`harness remove --eject` both delete it and its links: it teaches `./harnessw` commands that do not exist once the
wrapper is gone ([remove](remove.md#eject)).

## Shared skills

### When to use it

- The repository should carry skills your organization or you maintain elsewhere.
- Many repositories should get the same skill.

### How it works

The team installs shared skills into `.agents/skills/` with the tool it uses for that, and commits the result. Every
clone and every agent then has them without running anything, and a reviewer sees each skill's text in the diff that
adds it. The binary has no code for it: no command or profile field installs, updates or removes a shared skill.

The `skills` [plugin](plugins.md#skills) describes the `skills` CLI: with the plugin in the profile's `plugins:`,
[`harness doctor`](doctor.md) checks the CLI's version against the range the plugin supports. Installing, updating and
removing a skill stay the CLI's own commands, run by a person or an agent.

With the [`skills` CLI](https://github.com/vercel-labs/skills), which needs Node, a team installs a source and commits
both the skills and the CLI's lock file, `skills-lock.json`:

```sh
npx skills add acme/agent-skills
git add .agents/skills skills-lock.json
git commit -m "chore: install shared agent skills"
```

On a machine without Node, such as one that only builds a Terraform or Go repository, the same commands run on any
machine that has it, and the commit carries the skills to every clone.

To drop a shared skill, remove it with the tool that installed it, then commit the change. A `context` entry that still
names it is a [`harness doctor`](doctor.md) finding.

## Skills as standing context

An installed skill reaches a session in one of two ways:

| Way | When the agent gets it | Decided by |
| --- | --- | --- |
| The agent matches the skill's description and loads it | when the agent judges it relevant | the agent, from the description |
| A [`context`](context.md) entry names it | always, when matching files are read or edited, or when the person's message contains a listed word | the repository, deterministically |

A `context` entry names a skill by its name, the name of its directory under `.agents/skills/`:

```yaml
# .harness/config.yaml (a Node API)
context:
  always:
    - skill: coding-guidelines
```

A skill a `context` entry names that does not exist under `.agents/skills/` is a [`harness doctor`](doctor.md)
finding, and nothing is injected for it. A skill is injected as it is committed under `.agents/skills/`, whoever wrote
it; for a worker, as it is in the base commit. `harness` reads no installer's lock file, so a reviewer approves a
skill's content in the diff that adds or changes it ([ADR 0022](../adrs/0022-tool-integration.md)). Nothing is fetched
when a hook runs: a skill is injected only once it is installed and committed.

Skills written to be injected follow the [skills standards](../ux/skills-standards.md): a short body, self-contained,
instructions first, so they read correctly as a pointer or as injected content.

## Guidelines

- Do keep domain knowledge in repository skills you write and review; `harness` never generates them.
- Do commit installed skills and the installer's lock file, so every clone and every agent has them without running
  anything.
- Don't edit `.agents/skills/harness/SKILL.md`; render overwrites it. Put repository-specific guidance in `AGENTS.md`
  or a repository skill.
- Don't vendor the same skill by hand and through an installer; the installer will not know about the hand copy.
- Don't edit a shared skill in place: the next install from its source overwrites the edit. Change it at its source
  and reinstall.
- Do declare as standing context the skills that should apply without anyone invoking them, and leave the rest to the
  agent's own matching.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `doctor`: a skill `context` names does not exist | The skill is not installed, was removed, or the entry misspells its directory name | Install and commit the skill, or fix or remove the `context` entry |
| Claude Code does not list the harness skill | `.claude/skills/harness` missing, or the folder is not trusted | `harness render`; trust the folder |
| A private source fails to install | No git credentials for it on this machine | Configure access, rerun the installer |
