# Generated-content standards

Rules for anything harness writes into a repository. Readers of an adopted repository, with or without the binary,
must be able to tell what harness owns, see every change it makes, and get their repository back intact when it
leaves.

## Kinds of generated content

| Kind | Example | How ownership is marked |
| --- | --- | --- |
| Owned whole file that allows comments | `.codex/rules/harness.rules`, mise wrappers under `.mise/tasks/` | header line, plus the manifest |
| Owned whole file that cannot start with a comment | `.agents/skills/harness/SKILL.md` (its frontmatter comes first); JSON files | the manifest |
| Managed block inside a human file | `commands`, `files`, `memory-index`, `policy-summary` in `AGENTS.md` and `README.md`; `import` in `CLAUDE.md`; `ignore` in `.gitignore` | begin and end markers, plus the manifest |
| Owned keys inside a native file | `permissions.{allow,ask,deny}`, harness hook entries and rendered raw hook entries in `.claude/settings.json`; the equivalent keys and entries in `.codex/config.toml` and `.codex/hooks.json` | the manifest |
| Link | `.claude/skills/harness -> ../../.agents/skills/harness` | the manifest |
| State | `.work/` (including the lifecycle record `.work/lifecycle.jsonl`) | gitignored; never committed, never listed as content |

The manifest (`.agents/.harness/manifest.json`) is the record of ownership. Content not listed in it is not harness's,
whatever it looks like.

## Header

Owned files that allow comments start with exactly this line (after a shebang line where the file needs one):

```text
# generated by harness (schema 1): edit .agents/<source> and run harness render
```

- The comment syntax adapts to the file type; the words do not.
- `<source>` names the repository file that produces this output, so a reader knows where to make the change.
- The header carries the schema, never the binary version, date or user.

## Managed blocks

```markdown
<!-- harness:begin commands -->
…owned content…
<!-- harness:end commands -->
```

```text
# harness:begin ignore
…owned content…
# harness:end ignore
```

- Markdown uses HTML comments; `.gitignore`, YAML and TOML use `#` comments.
- Block ids come from a documented, closed set. An id is never renamed except through a schema migration.
- A file holds at most one block per id.
- Everything between the markers is owned by harness and replaced on render. Everything outside them is never read
  for writing, reordered or reformatted.
- A new block is appended at the end of the file. Once present, a block may be moved anywhere in the file by a person,
  and harness updates it where it is.
- Block content is derived from the repository files: tables, lists, one-line imports. It is never generated prose.
- The `.gitignore` block omits any path the repository tracks.

## Owned keys in native files

- harness changes only the keys it owns. Every other key, its value, its order and its formatting are preserved byte
  for byte.
- Owned permission lists belong to harness entirely: an entry added there by hand is drift. To keep it, add it to
  `policy.yaml`; adoption does this for entries that existed before harness.
- Hook entries are owned one by one. harness owns the entries that run the harness hook command and the native
  entries it renders from `raw` declarations in `hooks.yaml`. Hooks added by other tools or by hand are preserved where
  they are.
- A raw hook renders as a native entry that runs its own command, not the harness hook command, so it keeps working
  without the binary. It is recorded in the manifest as owned: a hand edit to it is drift, and `harness remove` removes
  it.
- Local override files (`.claude/settings.local.json`, `*.local.toml`) are never written or listed. They are read only
  by `harness scaffold --import local`.

## Determinism

- The same repository files, preset commit (as recorded in the manifest) and schema produce the same bytes on every
  supported operating system and with every binary release of the same major version
  ([compatibility-standards.md](compatibility-standards.md#rendered-output-across-releases)). The harness skill is the
  one exception: its content follows the binary that renders it.
- Generated content contains no timestamps, binary versions, usernames, hostnames, absolute paths or random values.
- Order follows the source file's declaration order where one exists, and a documented sort otherwise.
- Text files are UTF-8, use LF line endings and end with one newline.

## Idempotency and drift

- Running `harness render` twice in a row changes nothing the second time.
- A hand edit to owned content is drift. `harness render --check` exits 2 and names each file, block and key that
  drifted. `harness render` replaces the drifted content and lists what it replaced; `--dry-run` shows it first.
- Drift is detected by comparing against the manifest's hashes, so it is reported even when the repository files
  have not changed.
- The harness skill is refreshed by `harness render`. When the installed skill still matches its manifest hash but the
  binary embeds a newer one, the difference is not drift: `render --check` passes, `harness doctor` reports a note,
  and the next `harness render` refreshes the skill. A hand edit to the skill is drift like any other.

## Review

- Generated content is committed so that every change reaches review as a diff and a clone works without the binary.
- A change to one repository file produces the smallest rendered diff that expresses it; unrelated lines do not move.
- The binary commits in a repository only when a person runs `harness fleet <command> --deliver`: it commits the
  tool-owned changes on a new local branch `<branch_prefix><command>`, cut from the fetched default branch, then fires
  that repository's `deliver` actions. Any other commit, push or pull request is a lifecycle action the repository or
  its preset declares.
- Reviewers judge the source change (`policy.yaml`, `hooks.yaml`, `harness.yaml`); the rendered diff shows its effect
  on each agent.

## Removal

`harness remove` (or `harness remove --module <name>`) restores the repository to a working state without harness:

- It deletes the whole files and links the manifest lists, removes managed blocks including their markers, and
  removes owned keys from native files. Text and keys around them stay byte for byte.
- It never deletes a file the manifest does not list.
- A listed file whose content no longer matches its recorded hash was edited by hand. `remove` refuses it, names it,
  and exits 3 unless `--force` is given.
- Permission entries and hooks that adoption imported from native files are written back as plain native settings, so
  the agents keep behaving as before.
- `--dry-run` lists every path, block and key it would remove.
- After removal, `git status` shows only changes to content harness owned.
