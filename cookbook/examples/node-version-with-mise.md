# Node version through mise

This is a **proposed interaction**, not a working CLI or supported schema. In this cookbook, the [Node ingredient](../ingredients/node.yaml) uses mise. Its `@22` argument is the Node major, not a version of the ingredient definition.

```sh
the-cook init
./cook ingredient add git node@22 npm
./cook kitchen apply
```

The Node ingredient contributes to three files: `node_modules/` in `.gitignore`, `tools.node = "22"` in `mise.toml`, and `@types/node = "^22.0.0"` in `package.json` **only if that dependency already exists**. Git declares `owns: true` for `.gitignore`; the required mise ingredient declares it for `mise.toml`. That lets them create missing files without taking over unrelated content. npm is the selected package manager. No separate `mise-node` or `node-types` selection is needed for this cookbook's Node behavior.

The relevant parts of the resulting files would be:

```toml
# mise.toml
[tools]
node = "22"
```

```json
{
  "devDependencies": {
    "@types/node": "^22.0.0"
  }
}
```

For a repository already using `node@20`, the switch should take two cook commands:

```sh
./cook ingredient use node@22
./cook kitchen apply
```

`use` replaces the selected version of the same ingredient. `apply` reconciles its previous contributions: it changes the two versioned keys, preserves unrelated keys, and is harmless to repeat. A station could bundle an initial selection, but it does not control this version change. A session recipe is not needed to express the desired state.

## Where this sketch is incomplete

- Writing `mise.toml` requests Node 22 but does not install it. If the two cook commands promise a ready local runtime, `apply` must also invoke a mise-declared install action and report any failure.
- The selected npm ingredient must refresh `package-lock.json` after `package.json` changes. The lockfile is generated by npm, not templated by Node. A real two-command switch requires an npm-declared refresh action in `kitchen apply` and clear failure reporting. The current sketch does not define that action yet.
- If `package.json` or `@types/node` is absent, Node does not add the dependency. If the key was manually edited outside Cook after adoption, `apply` must report a conflict rather than silently overwrite it.
- If someone runs `mise use node@22` directly, Cook must import the change or report drift against its selected `node@20`; it must not silently restore 20.
- Following the development runtime is not right for every project. A package developed on Node 22 may still support Node 20. This cookbook's Node rule needs a way to opt out or bind `@types/node` to the minimum supported Node version instead.
- A monorepo may have several packages or Node targets. The ingredient needs explicit target paths before it can update more than one `package.json` safely.

This example stays within the generic `files` model: `append` contributes lines, `set` changes named TOML or JSON keys, and `owns: false` is the default. The binary does not need a special Node or mise case, but it does need parameter substitution, key-level reconciliation, and a defined way to invoke the selected package manager for generated files.
